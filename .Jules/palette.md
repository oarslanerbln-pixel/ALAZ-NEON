## 2026-04-07 - Custom Button Accessibility
**Learning:** When using Framer Motion to create interactive `motion.div` elements that act as buttons (like `TiltCard`), they lack default keyboard accessibility. Adding `role="button"`, `tabIndex={0}`, `onKeyDown` handlers for 'Enter' and 'Space', and Tailwind `focus-visible` classes is essential for screen readers and keyboard navigation.
**Action:** Ensure all custom interactive `div` or `motion.div` components meant to behave like buttons include proper ARIA roles, keyboard event handlers, and visible focus states.

## 2026-07-22 - Prisma 7 driver adapters + CLI/client version lockstep
**Learning:** `apps/backend/package.json` pinned `@prisma/client@^7.8.0` but `prisma@^6.3.1` (CLI) — Prisma requires the CLI and client major versions to match, and `prisma generate` failed with a missing wasm engine file until both were bumped to `^7.9.0`. Separately, Prisma 7 removed the `url` field from the `datasource` block in `schema.prisma` entirely (`prisma.config.ts` still holds the URL for Migrate/CLI); at runtime `PrismaClient` now requires an explicit driver adapter, e.g. `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })` from `@prisma/adapter-pg`.
**Action:** Keep `prisma` and `@prisma/client` on the same major version. When editing `schema.prisma`, don't add `url` back to the datasource block — configure the connection via `prisma.config.ts` (CLI) and a driver adapter passed to `new PrismaClient()` (runtime). Run `pnpm approve-builds --all` (or accept the `allowBuilds` entries in `pnpm-workspace.yaml`) after installing, or `prisma generate` fails to find its engine.

## 2026-07-22 - Express 4 async routes need explicit error handling
**Learning:** Express 4 does not catch rejected promises thrown from `async` route handlers. An unhandled Prisma error (e.g. database unreachable) inside a plain `async (req, res) => {...}` handler crashes the entire Node process instead of returning an error response — confirmed by reproducing it locally (an unreachable DB during `/auth/register` took the whole server down).
**Action:** Wrap every async Express route handler with a small `asyncHandler` utility (`apps/backend/src/lib/asyncHandler.ts`) that forwards rejections to `next(err)`, and register a catch-all error-handling middleware (4-arg signature) as the last `app.use()` in `index.ts` so failures return a JSON 500 instead of taking the process down.

## 2026-08-04 - tesseract.js v7 `createWorker` is pre-initialized; CDN dependency at runtime
**Learning:** In `tesseract.js@7`, `createWorker(langs, oem, options)` (`apps/frontend/src/components/UploadDocument.tsx`) already loads the language and initializes the engine by the time the returned promise resolves — the old `worker.load()` step is deprecated/no-op, calling `worker.recognize(image)` directly is enough. Progress comes through `options.logger`, which fires for every internal step (`loading tesseract core`, `loading language traineddata`, `initializing api`, `recognizing text`, …); only `status === 'recognizing text'` corresponds to the 0–1 `progress` of the actual OCR pass; the rest of the events also carry `progress` fields for their own sub-steps but as an aggregate misleads a single "% done" indicator. Also: by default `createWorker` fetches the `tur.traineddata` language pack and worker/core scripts from a CDN (jsdelivr) at runtime — the browser needs internet access on every scan unless `langPath`/`corePath`/`workerPath` are pointed at self-hosted assets under `public/`.
**Action:** Filter the `logger` callback to `m.status === 'recognizing text'` when driving a single progress percentage. Always `worker.terminate()` in a `finally` block to avoid leaking the worker. Remember the CDN dependency is a real constraint for the PWA's offline goal — self-hosting the traineddata/core files is still open (see roadmap Sprint 3b note).

## 2026-08-04 - `next-pwa` doesn't work with Turbopack; use the native `app/manifest.ts` route instead
**Learning:** `next-pwa` (was in `apps/frontend/package.json`, unused/never wired into `next.config.ts`) is a webpack plugin — it hooks service-worker generation into webpack's compile step via `withPWA()`. Next.js 16 uses Turbopack as the default (and, per `next build --webpack`/`--webpack` flag aside, effectively only well-supported) bundler; the framework's own current PWA guide (`node_modules/next/.../docs/01-app/02-guides/progressive-web-apps.md`) doesn't mention `next-pwa` at all and even flags its suggested successor (Serwist) as still webpack-only. `next-pwa` would have been silently inert here. The native replacement for installability is the `app/manifest.ts` file-convention route (returns `MetadataRoute.Manifest`) — confirmed by building that it's served at `/manifest.webmanifest`, not `/manifest.json` (so `layout.tsx`'s `metadata.manifest` must point there, not at a hand-placed `public/manifest.json`).
**Action:** Don't reach for `next-pwa`/Serwist on a Turbopack project. Use `app/manifest.ts` for the web manifest and, if actual offline caching is needed, a hand-written `public/sw.js` registered manually via `navigator.serviceWorker.register()` in a small client component (no bundler plugin involved — this is the same pattern Next's own push-notification guide uses). Also: no image tool (ImageMagick/`sharp`/rsvg-convert) was available in this environment; PWA icon PNGs were generated with a small standalone script (`apps/frontend/scripts/generate-pwa-icons.mjs`) that encodes raw pixel buffers via Node's built-in `zlib.deflateSync` — no new dependency needed for simple flat-color icons.

## 2026-08-04 - `@anthropic-ai/sdk` message content is a typed union — narrow before reading `.text`
**Learning:** `apps/backend/src/lib/anthropic.ts` calls `anthropic.messages.create(...)` to summarize OCR'd report text (Claude Haiku 4.5, no tools/thinking). The response's `message.content` is `ContentBlock[]`, a discriminated union (`text` | `thinking` | `tool_use` | …) — indexing `content[0].text` directly doesn't type-check and isn't safe at runtime either (a refusal or an unexpected block type would silently produce `undefined`). Also: an unset `ANTHROPIC_API_KEY` doesn't make the SDK throw at construction — `new Anthropic({ apiKey: undefined })` succeeds, and the missing-credential failure only surfaces (as a 401 from Anthropic) on the first actual request.
**Action:** Use `content.find((b) => b.type === 'text')` and check `block.type === 'text'` before reading `.text`, throwing a clear error otherwise. Check `process.env.ANTHROPIC_API_KEY` explicitly in the route handler *before* calling the summarizer, so a missing key returns a clean 503 with a Turkish message instead of an opaque failure surfacing from inside the SDK call.

## 2026-08-04 - JWT localStorage → httpOnly cookie migration: CORS credentials, SameSite, and the auth bootstrap round-trip
**Learning:** Migrated auth from `localStorage` + `Authorization: Bearer` to an httpOnly `token` cookie (`apps/backend/src/lib/authCookie.ts`, `middleware/auth.ts` now reads `req.cookies.token`). Three non-obvious pieces: (1) `cors({ origin: allowedOrigins, credentials: true })` — CORS rejects `credentials: true` combined with a wildcard origin, which is why `FRONTEND_URL` must stay an explicit allowlist, never `*`; the frontend's `fetch` calls also need `credentials: 'include'` on every request, or the browser won't send/accept the cookie cross-origin (frontend :3000 and backend :3001 are different origins even on the same host). (2) `secure: true` on the cookie makes the browser silently refuse to store it over plain `http://` — gated behind `NODE_ENV === 'production'` so local dev still works; deploys **must** set `NODE_ENV=production` or the cookie ships without `Secure`. (3) Since the token is no longer JS-readable, the frontend can't synchronously know "am I logged in" on mount the way `useSyncExternalStore` + `localStorage` did — `auth-context.tsx` now bootstraps by calling `GET /auth/me` in a `useEffect` and staying `isLoading: true` until it resolves, which adds one network round-trip before any protected page's own data fetch can start.
**Action:** When adding cookie-based auth to a split-origin frontend/backend: always pair `credentials: true` on the server CORS config with `credentials: 'include'` on every client fetch, and with an explicit (never wildcard) CORS origin allowlist. Treat `NODE_ENV=production` as a deployment requirement, not a default — document it in `.env.example`. **Scoping note:** did not add a separate CSRF token (double-submit cookie) on top of this — `SameSite=Lax` already blocks browsers from attaching the cookie to cross-site `fetch`/XHR requests (Lax only allows the cookie on top-level cross-site *navigations*, which this JSON-only API never uses), and the CORS allowlist blocks cross-origin `fetch` from completing anyway. This is considered adequate for a fetch-only JSON API; revisit if any endpoint ever accepts classic HTML form POSTs.

## 2026-08-04 - Self-hosting tesseract.js assets: jsdelivr is proxy-blocked here, use the npm registry tarballs instead
**Learning:** To make OCR work offline (per the Sprint 3b note), needed to vendor `tesseract.js`'s worker script, WASM core, and `tur.traineddata` instead of letting `createWorker` fetch them from `cdn.jsdelivr.net` at scan time. Two non-obvious things: (1) **`cdn.jsdelivr.net` is blocked by this environment's outbound proxy** (`curl` → 403, confirmed via `$HTTPS_PROXY/__agentproxy/status` → `recentRelayFailures` showing `connect_rejected` for that host) — but `registry.npmjs.org` is allowlisted, and the exact files jsdelivr would have served are just the *contents of published npm packages* (`tesseract.js-core` — already an installed transitive dependency — and `@tesseract.js-data/<lang>`, which is not transitively installed and had to be added as a devDependency). `npm pack @tesseract.js-data/tur` and inspecting the tarball showed the file jsdelivr's URL path (`.../tur/4.0.0_best_int/tur.traineddata.gz`) actually resolves to a **folder inside the npm package**, not an npm dist-tag version — the installed package version (e.g. `1.0.0`) is unrelated to that `4.0.0_best_int` path segment. (2) `corePath` can point at a local directory exactly like it points at a CDN base — `tesseract.js`'s browser `getCore.js` runs `wasm-feature-detect` (SIMD support) at runtime and appends the right filename (`tesseract-core-simd-lstm.wasm.js` / `-relaxedsimd-lstm.wasm.js` / plain) itself, so hosting all three `*-lstm.wasm.js` variants under one `public/` folder and passing `corePath: '/tesseract-core'` is enough — no need to detect the browser and pick a file yourself. Confirmed end-to-end with a Playwright smoke test (`chromium-cli` wasn't available in this environment): all three asset requests (`worker.min.js`, the SIMD-detected core variant, `tur.traineddata.gz`) resolved from `localhost`, zero requests to jsdelivr, and OCR correctly extracted synthetic canvas-rendered text. Also: a `/* ... */` JS block comment containing the literal substring `*/` inside prose (e.g. writing `tesseract*/` to mean "paths starting with tesseract") terminates the comment early and breaks the next line as code — this crashed `vendor-ocr-assets.mjs` on first run with a cryptic `SyntaxError: Unexpected identifier`.
**Action:** When a CDN is unreachable but the asset is inside a published npm package, reach for `npm pack <pkg>@<version>` + `tar -xzf` to inspect the real file layout rather than assuming the CDN URL structure maps 1:1 to npm semver. Vendor generated/third-party binary assets via a `postinstall` script that copies from `node_modules` into `public/`, gitignore the destination folders (keeps them out of git history — ~14MB here — while staying reproducible via `pnpm install`), and exclude those paths from ESLint's `globalIgnores` since minified vendored `.js` files will otherwise flood lint output. Never write a literal `*/` inside a block comment's prose, even mid-sentence.

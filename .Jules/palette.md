## 2026-04-07 - Custom Button Accessibility
**Learning:** When using Framer Motion to create interactive `motion.div` elements that act as buttons (like `TiltCard`), they lack default keyboard accessibility. Adding `role="button"`, `tabIndex={0}`, `onKeyDown` handlers for 'Enter' and 'Space', and Tailwind `focus-visible` classes is essential for screen readers and keyboard navigation.
**Action:** Ensure all custom interactive `div` or `motion.div` components meant to behave like buttons include proper ARIA roles, keyboard event handlers, and visible focus states.

## 2026-07-22 - Prisma 7 driver adapters + CLI/client version lockstep
**Learning:** `apps/backend/package.json` pinned `@prisma/client@^7.8.0` but `prisma@^6.3.1` (CLI) — Prisma requires the CLI and client major versions to match, and `prisma generate` failed with a missing wasm engine file until both were bumped to `^7.9.0`. Separately, Prisma 7 removed the `url` field from the `datasource` block in `schema.prisma` entirely (`prisma.config.ts` still holds the URL for Migrate/CLI); at runtime `PrismaClient` now requires an explicit driver adapter, e.g. `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })` from `@prisma/adapter-pg`.
**Action:** Keep `prisma` and `@prisma/client` on the same major version. When editing `schema.prisma`, don't add `url` back to the datasource block — configure the connection via `prisma.config.ts` (CLI) and a driver adapter passed to `new PrismaClient()` (runtime). Run `pnpm approve-builds --all` (or accept the `allowBuilds` entries in `pnpm-workspace.yaml`) after installing, or `prisma generate` fails to find its engine.

## 2026-07-22 - Express 4 async routes need explicit error handling
**Learning:** Express 4 does not catch rejected promises thrown from `async` route handlers. An unhandled Prisma error (e.g. database unreachable) inside a plain `async (req, res) => {...}` handler crashes the entire Node process instead of returning an error response — confirmed by reproducing it locally (an unreachable DB during `/auth/register` took the whole server down).
**Action:** Wrap every async Express route handler with a small `asyncHandler` utility (`apps/backend/src/lib/asyncHandler.ts`) that forwards rejections to `next(err)`, and register a catch-all error-handling middleware (4-arg signature) as the last `app.use()` in `index.ts` so failures return a JSON 500 instead of taking the process down.

## 2026-07-24 - `dotenv.config()` after other imports never fires in time
**Learning:** `apps/backend/src/index.ts` called `dotenv.config()` textually below `import authRouter from './routes/auth.js'` etc. ES module imports are hoisted and fully evaluated before any of the importing module's own statements run, so `auth.ts` → `lib/prisma.ts` (which builds `new PrismaPg({ connectionString: process.env.DATABASE_URL })` at module-load time) always ran with `DATABASE_URL` still `undefined`. This silently broke every DB query locally (Prisma reported a confusing `P1010`/"access denied" instead of a clear missing-env error) whenever config came from a `.env` file — it only worked in environments where the platform injects env vars directly into `process.env` before Node starts.
**Action:** Put `dotenv.config()` in its own module (`src/env.ts`) and make it the very first `import` in `index.ts` (`import './env.js';` before any other import). Sibling static imports in one file evaluate in source order, so this guarantees env vars are populated before any other module reads them at load time. Never rely on textual position of a bare statement relative to import statements to control ordering.

## 2026-07-24 - Node 22 breaks `ts-node --esm`; use `tsx` instead
**Learning:** `apps/backend`'s `dev` script (`nodemon --exec ts-node src/index.ts`) always crashed with `ERR_MODULE_NOT_FOUND` on the very first relative import, because plain `ts-node` doesn't do ESM resolution for a `"type": "module"` package. Switching to `node --loader ts-node/esm` avoided that error but crashed with an opaque `[Object: null prototype]` uncaught exception — `ts-node`'s custom ESM loader hooks are broken on Node 22 (a known upstream incompatibility with Node's newer module customization hooks).
**Action:** Replaced `ts-node` with `tsx` (`nodemon --exec tsx src/index.ts`) for the backend dev script. `tsx` works out of the box with ESM + Node 22 and needs no loader flags or extra config.

## 2026-07-24 - tesseract.js browser worker/core/lang data default to jsdelivr CDN
**Learning:** `tesseract.js` v7's browser build lazy-loads its worker script, wasm core, and language traineddata from `cdn.jsdelivr.net` at runtime unless `workerPath`/`corePath`/`langPath` are overridden — this is intentional upstream design (keeps the app bundle small), not a bug, but it means OCR silently fails wherever `cdn.jsdelivr.net` is unreachable (corporate proxies, ad blockers, this repo's own sandboxed test environment). In Node.js, by contrast, the wasm core loads from the locally installed `tesseract.js-core` package with no network call, so `createWorker('tur', ...)` can be exercised in plain Node (pointing `langPath` at a local directory containing `tur.traineddata.gz`, e.g. unpacked from the `@tesseract.js-data/tur` npm package) to verify OCR logic without touching the CDN at all.
**Action:** Left `apps/frontend/src/components/UploadDocument.tsx` on the CDN defaults (standard practice for a web app with real internet access) but be aware that any sandboxed/offline testing of the scan flow needs either network access to jsdelivr or a Node-side check like the one above. If MediSade later needs offline/PWA-reliable OCR, self-hosting these three asset paths under `public/` is the fix — not attempted here since it wasn't asked for and adds real repo size.

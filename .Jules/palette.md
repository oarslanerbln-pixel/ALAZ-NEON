## 2026-04-07 - Custom Button Accessibility
**Learning:** When using Framer Motion to create interactive `motion.div` elements that act as buttons (like `TiltCard`), they lack default keyboard accessibility. Adding `role="button"`, `tabIndex={0}`, `onKeyDown` handlers for 'Enter' and 'Space', and Tailwind `focus-visible` classes is essential for screen readers and keyboard navigation.
**Action:** Ensure all custom interactive `div` or `motion.div` components meant to behave like buttons include proper ARIA roles, keyboard event handlers, and visible focus states.

## 2026-07-22 - Prisma 7 driver adapters + CLI/client version lockstep
**Learning:** `apps/backend/package.json` pinned `@prisma/client@^7.8.0` but `prisma@^6.3.1` (CLI) — Prisma requires the CLI and client major versions to match, and `prisma generate` failed with a missing wasm engine file until both were bumped to `^7.9.0`. Separately, Prisma 7 removed the `url` field from the `datasource` block in `schema.prisma` entirely (`prisma.config.ts` still holds the URL for Migrate/CLI); at runtime `PrismaClient` now requires an explicit driver adapter, e.g. `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })` from `@prisma/adapter-pg`.
**Action:** Keep `prisma` and `@prisma/client` on the same major version. When editing `schema.prisma`, don't add `url` back to the datasource block — configure the connection via `prisma.config.ts` (CLI) and a driver adapter passed to `new PrismaClient()` (runtime). Run `pnpm approve-builds --all` (or accept the `allowBuilds` entries in `pnpm-workspace.yaml`) after installing, or `prisma generate` fails to find its engine.

## 2026-07-22 - Express 4 async routes need explicit error handling
**Learning:** Express 4 does not catch rejected promises thrown from `async` route handlers. An unhandled Prisma error (e.g. database unreachable) inside a plain `async (req, res) => {...}` handler crashes the entire Node process instead of returning an error response — confirmed by reproducing it locally (an unreachable DB during `/auth/register` took the whole server down).
**Action:** Wrap every async Express route handler with a small `asyncHandler` utility (`apps/backend/src/lib/asyncHandler.ts`) that forwards rejections to `next(err)`, and register a catch-all error-handling middleware (4-arg signature) as the last `app.use()` in `index.ts` so failures return a JSON 500 instead of taking the process down.

## 2026-08-04 - tesseract.js v7 `createWorker` is pre-initialized; CDN dependency at runtime
**Learning:** In `tesseract.js@7`, `createWorker(langs, oem, options)` (`apps/frontend/src/components/UploadDocument.tsx`) already loads the language and initializes the engine by the time the returned promise resolves — the old `worker.load()` step is deprecated/no-op, calling `worker.recognize(image)` directly is enough. Progress comes through `options.logger`, which fires for every internal step (`loading tesseract core`, `loading language traineddata`, `initializing api`, `recognizing text`, …); only `status === 'recognizing text'` corresponds to the 0–1 `progress` of the actual OCR pass; the rest of the events also carry `progress` fields for their own sub-steps but as an aggregate misleads a single "% done" indicator. Also: by default `createWorker` fetches the `tur.traineddata` language pack and worker/core scripts from a CDN (jsdelivr) at runtime — the browser needs internet access on every scan unless `langPath`/`corePath`/`workerPath` are pointed at self-hosted assets under `public/`.
**Action:** Filter the `logger` callback to `m.status === 'recognizing text'` when driving a single progress percentage. Always `worker.terminate()` in a `finally` block to avoid leaking the worker. Remember the CDN dependency is a real constraint for the PWA's offline goal — self-hosting the traineddata/core files is still open (see roadmap Sprint 3b note).
